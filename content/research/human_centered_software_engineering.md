Software engineering tools are most useful when they account for the people who use them. My research examines both how developers' work can be observed and how their knowledge can become an input to automated analysis.

One way to understand development work is to observe it directly. In [[research/bibliography/identifying_wasted_effort_in_the_field_via_developer_interaction_data|our study of wasted effort]], we collected detailed IDE interaction traces from an industrial project and constructed micro-productivity profiles to characterize changes in productivity across milestones and application layers. This complements the structural perspective on software described in [[research/bibliography/software_systems_their_engineers_and_their_testers|Software Systems, Their Engineers and Their Testers]], which considers how analysis of program and test organization can help developers identify problematic code.

A second direction is to involve developers in the analysis itself. Spectrum-based fault localization ranks suspicious program elements, but a conventional ranking does not necessarily exploit the knowledge a developer acquires while debugging. Our work on [[research/bibliography/using_contextual_knowledge_in_interactive_fault_localization|contextual knowledge in interactive fault localization]] and [[research/bibliography/interacting_with_interactive_fault_localization_tools|interaction with fault localization tools]] investigates feedback as a way to influence this process. [[research/bibliography/experiments_with_interactive_fault_localization_using_simulated_and_real_users|Experiments with simulated and real users]] examine this interactive approach, while [[research/bibliography/formal_notations_and_terminology_for_users_feedback_and_its_specialization_for_interactive_fault_localization|formal notations for user feedback]] address how such feedback can be represented. [[research/bibliography/on_context_switching_in_spectrum_based_fault_localization|Context switching in spectrum-based fault localization]] considers another aspect of the developer's debugging experience.

The interaction must also fit the development environment. Our work on [[research/bibliography/on_the_integration_of_spectrum_based_fault_localization_tools_into_ides|integrating fault localization into IDEs]], [[research/bibliography/poster_aiding_java_developers_with_interactive_fault_localization_in_eclipse_ide|aiding Java developers in Eclipse]], and the [[research/bibliography/ifl_for_eclipse_a_tool_to_support_interactive_fault_localization_in_eclipse_ide|iFL for Eclipse tool]] addresses the practical interface between the analysis and its users. The underlying analysis methods are discussed in [[research/software_analysis_and_quality_assurance|software analysis and quality assurance]].

Human expertise is relevant beyond debugging: [[research/bibliography/capturing_expert_knowledge_to_guide_data_flow_and_structure_analysis_of_large_corporate_databases|our work on expert-guided corporate database analysis]] considers domain knowledge in structural analysis, and [[research/bibliography/towards_project_aware_actionability_detection_for_coding_rule_violations|project-aware actionability detection]] uses active learning to account for which warnings matter in a particular project. Collaboration is another aspect of this perspective, explored through [[research/bibliography/codemetropolis_a_minecraft_based_collaboration_tool_for_developers|CodeMetropolis as a shared virtual environment for developers]], connecting this topic to [[research/software_visualization_and_comprehension|software visualization and comprehension]].
